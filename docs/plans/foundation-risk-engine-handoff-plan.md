## Intent and architectural decision

Implement the full **PHP-side distributed credential-stuffing mitigation** as an **opt-in, cohesively integrated Foundation Security/Risk capability** (working namespace `Infocyph\Foundation\Security\Risk`, refine after type/file budget review). No separate `infocyph/riskkit` package. Foundation already has `Auth\Authentication\Login\Authenticator`, `Auth\Authentication\Lockout\LockoutManager`, `Auth\Device\DeviceManager`, audit services and required CacheLayer dependency. Reuse them rather than inventing another login system, device registry, event framework, crypto library or provider abstraction for each signal.

Keep the domain policy internally independent of HTTP Request/Response objects: normalized, trusted network/client facts in; bounded immutable risk result out. Webrick already provides optional `RiskAdmissionMiddleware(callable $evaluator)` and `RiskDecision` for route-level allow, challenge, deny, unavailable and shadow behavior. **Never make Webrick depend on Foundation**. Foundation supplies a callback/composition adapter into Webrick only when the application enables it. For non-Foundation hosts, Webrick continues accepting any host evaluator. Webrick owns HTTP/admission/router semantics; Foundation owns risk scoring and auth outcomes; CacheLayer owns cache primitives only. Runwire, Epicrypt, InterMix, ReqShield and Omnibus require **no source changes** for this plan.

Do not add an always-on auth route, required CAPTCHA vendor, Redis extension, application secret, account DB or external service to Webrick. Foundation's module must be disabled by default and must not alter existing login/lockout/device semantics until explicitly configured. If risk policy is globally deployed by a host, it should cover all intended authentication entry points, not silently only a hardcoded `/login`.

## Storage contract — any CacheLayer adapter, truthful guarantees

**Mandatory prominent documentation warning:** The host may configure **any CacheLayer cache adapter**, including custom adapters. Real distributed credential-stuffing protection across PHP workers/hosts requires a **shared authoritative backend** with appropriately qualified atomic operations, expiry, failure handling and consistency domain. An in-process array/WeakMap cache, APCu, null store, tiered cache or insufficiently coordinated filesystem is not equivalent to a distributed authority. **Do not ban adapter selection by name**, but also **do not claim distributed anti-replay or global hash-capacity isolation without effective guarantees**. CacheLayer's `isAuthoritative()` alone is not proof of cross-process sharing.

**Existing dependencies suffice; do not change CacheLayer.** Use `CacheInterface` or an appropriate PSR cache interface for ordinary state/telemetry, and probe `AtomicCacheProviderInterface::atomic()` for `setIfAbsent()`, `compareAndSet()`, and `getAndDelete()`. Where relevant, inspect `AuthenticationStateCacheInterface::{isFailOpen,hasPayloadIntegrity,isAuthoritative,authenticationStateLock}` and lock provider ownership. Prefer caller-configured `CacheOptions(failOpen:false)` for authoritative security operations. Never implement atomic consume or compare-and-swap with ordinary `get()` followed by `set()`. Preserve the injected adapter and its namespace/options; no hidden Redis factory or hardcoded adapter whitelist. `AtomicCounters::redis()` is **not** the universal storage contract.

**Per-operation failure policy:** Risk telemetry and familiarity can run in bounded best-effort mode, with explicit uncertainty/reduced score confidence. One-time CAPTCHA proof redemption/clearance, authoritative device-trust revocation and global password-hash lease coordination must **fail closed** when their necessary shared atomic/authoritative capability is missing or unavailable; a different caller-supplied capable cache/coordinator is permitted. An overloaded or uncoordinated request must never reach expensive password hashing because an adapter happens to be local. Preserve current Webrick `RiskDecision::unavailable()` response behavior rather than changing 503 into allow. Shadow evaluations are observational and never spend a token, lease or counter.

**Candidate algorithms, to validate before committing public APIs:** fixed/sliding time buckets for HMAC-pseudonymized JA4/prefix/ASN/account failures; bounded CAS loops and TTL windows rather than global read-modify-write; one-use signed clearance plus atomic claim/consume and an expiry margin; finite-slot concurrency leases with unique ownership tokens, bounded acquisition/renewal and owner-matched CAS release (not unconditional delete of a slot another worker acquired); backend and process-crash/stale-lease tests. These primitives are single-key atomic; do not promise cross-key transactions or perfect exactly-once outcome feedback. Never assume a lease still owns CPU work after TTL expiry. Qualification depends on backend topology, not an advertised method alone.

## Layer-by-layer functional contract

| Layer | Foundation implementation | Explicit boundary |
| --- | --- | --- |
| Trusted source signals | Validate typed attested edge inputs: normalized IP/IPv4-/24/IPv6-prefix, optional JA4, ASN, claimed User-Agent, tenant/route purpose; bound sizes and reject malformed data | TLS ClientHello fingerprint is calculated by a **real edge/CDN capability**, not by PHP or an incoming `$http_ssl_ja4` header; trusted proxy and direct-origin isolation configured by deployer/Webrick |
| Risk scoring | Configurable weighted signals (+60 curated UA/JA4 inconsistency, +25 unfamiliar JA4, +25–50 failed-signature velocity, +25 subnet/ASN concentration, −50 **verified** trust), safe reason codes, floor 0, tiers <30 allow / 30–69 challenge / >=70 deny | JA4 is correlation, not user/device authentication; no false UA mismatch without qualified map; unknown fingerprints do not automatically block |
| Redis-independent telemetry | CacheLayer-backed bounded counters/windows, HMAC-scoped keys, tenant/purpose separation and backend-failure modes | No raw JA4/IP/account/token in cache-key names/logs; no assumption of Redis or multi-key atomicity |
| Challenge/provider | Optional configured HTTPS proof verifier with strict TLS, approved destinations, no redirects/SSRF, bounded body/timeouts, cancellation, expected hostname/action/proof tenant | Vendor credentials and destination come only from host config; no user-supplied provider URL; provider outage never authorizes login |
| Proof clearance | One-time shared proof digest claim and/or issued clearance with signed purpose/expiry and qualified network binding; a spent proof stays spent on wrong password | Requires qualified atomic state, domain-wide replay protection and no unsafe local-cache fallback |
| Device trust | Time-limited, HMAC-signed versioned score-relief cookie with secure flags, tenant/account/purpose binding, rotation/revocation and optional attested JA4 | Separate from login/remember-me authentication credentials; only issue after proven auth success, never override hard deny |
| Closed-loop feedback | Confirmed authentication success/failure recorded once per attempt into scoped behavioral windows | Reuse Foundation login events and existing lockout audit; do not guess from arbitrary HTTP 401 or double-count retries |
| Password-hash isolation | Global/cache-coordinated bounded hash-admission lease, bounded wait, safe overload handling, per-process defense, owner-safe release/expiry | A semaphore does not make blocking bcrypt/Argon2 asynchronous; isolate CPU work in host-designated PHP-FPM/process pools |
| Observability | Safe reasons, sampled counters, failure-mode and capacity metrics, optional event hooks | No PII, raw secrets, client proof contents or credentials; no synchronous Omnibus requirement |

**Protocol/security precedence:** independent hard deny and resource-capacity constraints take precedence over cookie score relief and CAPTCHA success. Trusted-device cookies must not be minted on a failed auth attempt. A proof authenticates a challenge attempt, not a user. Score telemetry may degrade to best effort; authentication authorization, replay and capacity safeguards do not. Do not create a globally trusted identity from ordinary forwarded headers.

## Existing Foundation extension points to reuse

- `src/Auth/Authentication/Login/Authenticator.php`: explicit pre-password guard around `PasswordVerifierInterface::verify()`, and post-result callback for both known and unknown account attempts as appropriate without enumeration. Review exact historical behavior before changing the method signature; prefer an optional scoped composition/decorator over a mandatory constructor dependency.
- `src/Auth/Authentication/Lockout/LockoutManager.php`: already records lockout counts. Keep risk velocity signals separate from account lockout decisions; reuse authenticated outcomes and audit data instead of double-incrementing lockouts.
- `src/Auth/Device/DeviceManager.php`: existing device registration, trust and revocation. Bind risk-cookie score relief to verified device status without creating an incompatible second device registry.
- `src/Auth/AuthServiceProvider.php` and its internal registrar graph: gate the optional risk feature behind explicit user configuration and dependency injection; no startup/network work when disabled.
- `src/Auth/Adapter/CacheLayer/AtomicCounterStore.php`: existing bridge to a Redis/Valkey convenience counter; do **not** make this bridge the only choice for risk telemetry because all CacheLayer adapters must remain selectable.
- `resources/config/security.php`: compose risk thresholds, timeouts, edge provenance, storage roles, provider/trust secret resolution and operator-documented failure policy; secrets supplied by the application, never hardcoded or written into documentation.
- Foundation's existing application tests and authentication docs: extend rather than fork the general sign-in, lockout, device, token and deployment material.

## Operator documentation requirements

Publish brief, accurate configuration for NGINX, Caddy, CDN and proxy-provider variations, plus a **no-JA4** fallback. NGINX's `$http_*` variables read incoming request headers; they **do not calculate TLS JA4**. A CDN/module explicitly capable of computing JA4 must overwrite client-supplied identity headers on the trusted hop. Caddy similarly needs a real JA4 source or plugin; `reverse_proxy` forwarding alone is not a fingerprint engine. Lock origin traffic to authorized trusted edge, configure forwarded-IP chain, and use mTLS/restricted network transport when available. Do not ship misleading copy-paste spoofable header examples. Explain trusted-device token and CAPTCHA provider key provisioning, cookie security, fail-open telemetry vs fail-closed proof/hash guard, local dev vs distributed production.
